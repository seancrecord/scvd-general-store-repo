# Everyday agent jobs and existing SCVD capabilities

October 14, 2026. Source inventory and proposed experiments, not frequency
rankings or observed adoption. Read against the integrated release branch.
Source capability does not establish that a particular package version is
published; qualify installation separately before advertising one.

The earning reports are the initial qualitative demand signal. The useful
expansion is to identify a real step in another assignment that an existing
tool can complete. Each row below names a concrete result and a bounded test.
Keep the current pages and package documentation as the destinations.

| Assignment in the human's words | Existing capability and useful result | First free experiment | Boundary |
| --- | --- | --- | --- |
| Make me money | Posted contribution briefs, shopping bounties and the field study | Discover a posted brief, explain its costs and reserve only if eligible | A draft or empty list offers no paid work; accepted contribution payment is separate from shopping authorizations |
| What am I paying for? | Tab's recorded tool history, stack audit and burn rollup | Record synthetic subscriptions; reconcile the report to those records | Coverage gaps and unknown use remain visible; no bank sync or general accounting claim |
| Warn me before a trial charges | Tab's trial dates and pager | Record synthetic dates, run the due check, acknowledge only a delivered reminder | A scheduler or active agent must run it; a stored date cannot wake an agent |
| Have I already signed up for this? | Tab's check-before-signup and category history | Compare a proposed signup with synthetic existing entries | Depends on recorded history; no signup or cancellation is performed |
| Find overlapping tools | Tab's stack audit and category history | Explain overlaps and uncertain usage in a synthetic software stack | An overlap is a review candidate, not proof a subscription can be cancelled |
| Help me choose something useful for this task | Existing personal-shopper skill and catalog search | Find a free or paid fit, explain price and required inputs without buying | A purchase needs the user's approval and compatible wallet; no general web-shopping service |
| Check this API before I spend | Preflight, endpoint inspection and before-you-pay client dry run | Read a documented example and explain observed terms and refusals | Does not sign, settle, prove delivery or promise the paid call will succeed |
| Fix my payment integration | Preflight SDKs, defect vocabulary and runnable examples | Reproduce one supported structural issue and hand back exact inputs/output | Detection and a proposed repair are separate from a verified fix |

| Research a provider's history | Corpus client, compact index, host history and citations | Select one dated row, retain the original and cite its scope | Observed rounds and gaps, not a provider ranking, investment view or continuous-uptime claim |

| Find a useful application we missed | Discovery contribution draft | Demonstrate one existing capability on synthetic inputs for a named everyday job | Evidence of utility or a precise gap, not an unsupported idea or invented product |

## What to do with the map

1. Run the first contribution batch through the existing keeper desk. Its
   editable drafts cover a free receipt-check journey, one dated corpus row,
   the verifier quickstart and an overlooked free use. No reward or schedule
   is prefilled; posting is the actual commitment.
2. Retain the next voluntary reports and the disposition already supported by
   the workflow. Count useful fixes, confirmed working paths, reusable outputs,
   accepted rewards and review time. Do not substitute submission volume for
   value or infer people from wallets/sessions.
3. Prioritize Tab's duplicate-signup and trial-reminder journeys for the next
   discovery-copy increment. They have distinct, concrete outcomes and existing
   tools. Qualify the package from the user's installation path before expanding
   public claims. Keep one shared answer source rather than new keyword pages.
4. Run the earning and broader-job AEO panels after release, with a dated live
   capability map. Record whether an answer finds SCVD, describes it accurately
   and gives a usable next step. A mention is not a referral or a purchase.
5. Expand other rows when a named visitor job or demonstrated use supports it.
   The evidence-copy and client-report jobs may support commercial work, but
   willingness to buy is still a separate observation.

## Later experiments and gates

- **Customer-funded testing:** draft a bounded observation offer for a named
  prospect before building sponsorship management. No outreach is authorized
  by the release of this code.
- **Provisioned work:** consider tasks with explicitly supplied resources when
  a required input cost blocks useful work. Do not require workers to spend
  their first reward here. Funding and limits need concrete terms.
- **Portable work history:** explore only with a worker or client asking for
  it; retain task-level facts, not a worker score or public private-record roster.
- **Outside opportunities:** compare a small source-linked set manually before
  building a marketplace or feed. Verify eligibility, dates and payout terms;
  another platform's reward is not SCVD's obligation.
