# ERC-8004 agent 86957 — the registration file and the one transaction

**Status 2026-09-15: DONE, both halves.** `setAgentURI` landed from the
owner wallet in Base block 51350363 at 16:34:33 UTC:

    tx  0xf30142af2a953d553cfd136b06604b733031bb0ab5b6ec988df45caf433548cb

That hash was read out of the registry's own `URIUpdated` log for this
agent rather than taken from anybody's word for it. The two
instruments now pass:

    tokenURI(86957) = "https://scvd.store/.well-known/agent-registration.json"
    that document's registrations[0] = {86957, eip155:8453:0x8004A169…a432}

The chain names the document and the document names the agent, so the
agent and the domain are bound in both directions. The explorer that
read "Unconfigured" now reads the store's name, its nine services, and
the OASF entry's four skills and two domains.

What follows is the record of how it was done, kept because the next
person to move a `tokenURI` — ours or somebody else's — needs it.

**Status 2026-09-14 (superseded):** the file half is in this repository
and ships with the next deploy. The chain half is one transaction from
the owner wallet and has not been sent. Quoted rather than deleted: a
document that only ever shows its current answer is not the kind this
store publishes.

## What was actually wrong

The brief that opened this said the agentURI "resolves to
`atlas.json`". Read on-chain, it does not:

    tokenURI(86957) = "https://scvd.store"

The bare origin. What made the brief *look* right is that the origin
content-negotiates — `Accept: application/json` on `https://scvd.store`
returns the atlas, a `schema.org` `Collection`. So an explorer sending
a JSON Accept header gets the atlas, one sending a browser Accept
header gets storefront HTML, and neither document carries `type` or
`registrations`. The registration was never malformed. It pointed at a
URL that answers a different question, and every reader said so.

The distinction matters for the fix: the bug is the *target* of the
URI, not its contents, so nothing on the origin needed correcting —
something needed adding, and then the pointer needed moving.

      -H 'content-type: application/json' \

`0x153ad` is 86957. Mis-convert that and the call reverts

exist" and is not.

### The agent wallet is already correct — there is nothing to do

The plan that opened this carried an optional fifth step: bind the
agent wallet to the store's payTo. **It is already bound, and no
transaction should be sent.**

`getAgentWallet(86957)` reads `0xDD35…9bd0`. The live 402 on
`/api/buy/hello` quotes `payTo: 0xDD350976B8cfFc65938C0464d39A2C78BE079bd0`
on Base, Polygon, Arbitrum and World. Same address. The ERC explains
why without anyone having arranged it: `agentWallet` is reserved, and
is *initially set to the owner's address* at mint. The store minted
86957 from the wallet buyers already pay, so identity and payment
address were bound at mint.

Worth recording for the day it isn't: `setAgentWallet` is **not** the
"same one-tx shape" as `setAgentURI`. Its signature is

    setAgentWallet(uint256 agentId, address newWallet, uint256 deadline, bytes signature)

and the `signature` is an EIP-712 attestation *from the new wallet's
key* (ERC-1271 for contract wallets) proving control. Pointing the
agent at an address the owner does not hold keys for is not possible,
by design. Note also that `agentWallet` is **cleared automatically on
transfer** — if 86957 ever changes hands, the new owner re-proves the
wallet or it reads as the zero address.

## The file half — `/.well-known/agent-registration.json`

Built in `src/services/agent-registration.ts`, served from
`src/routes/well-known.ts`, pinned by `test/agent-registration.spec.ts`.

**Why that path, precisely.** It is not a neighbourhood choice. The ERC
names this exact path under "Endpoint Domain Verification": an agent
proves it controls an endpoint's domain by serving a file there whose
`registrations` list matches the chain. The spec then says the check is
unnecessary when the endpoint-domain is the same domain serving the
primary registration file. Serving the *full* file at this path and
pointing agentURI at it collapses both jobs into one document — it is
the registration file, and it is its own domain proof for every
scvd.store endpoint named inside it. A second copy at another URL would
be a second thing to keep in sync for no gain.

**Every field derives.** The name is `STORE_SERVICE_NAME`, the
description is `registryDescription()`, the protocol versions come
from the constants the live doors use. A registration file is copy that
travels furthest — an explorer caches it and it becomes the store's
identity in somebody else's index — so the draft's hand-written name
and freshly-written description were the one thing in it that had to
go. `metadata.ts` warns about exactly that drift in its own comments.

The description started as `STORE_METADATA.description` and was cut to
a registry budget on 2026-09-15: the canon is ~900 characters written
for a reader that fetches a whole document, and an explorer card
collapses after three lines. `registryDescription()` in
`store/identity-lead.ts` is the same identity at ~410 — one more
length of one account, never a second opinion.

**`supportedTrust` is deliberately absent.** The field is OPTIONAL and
the ERC is explicit: absent or empty means the registry is used "only
for discovery, not for trust". Each of the three values —
`reputation`, `crypto-economic`, `tee-attestation` — asserts
participation in a mechanism this store has not wired to anything.
Declaring one because it reads well is an unaudited claim published at
machine scale, which is the failure this store sells a desk for
catching in other people's metadata. It is one line to add on the day a
trust model is connected, and it is the keeper's call. The spec test
fails if it appears without that decision.

Omitting it does **not** stop the reputation registry from recording
feedback against 86957.

## The chain half — the one transaction

**This was sent on 2026-09-15** (block 51350363, above). What follows
is the procedure as it was run, kept because re-pointing the URI is a
thing that will happen again — a domain move, a path change, a switch
to a `data:` URI — and the gate below is the part that matters each
time.

**Send only after the deploy is live.** A URI that 404s is worse than
the bare origin, which at least returns a real document. Gate:

    curl -s -o /dev/null -w '%{http_code}\n' \
      https://scvd.store/.well-known/agent-registration.json

`200` and nothing else, before any transaction. It answered `404` when
this was written and `200` from the deploy of 2026-09-15, which is what
released the transaction below.

Then, from `0xDD350976B8cfFc65938C0464d39A2C78BE079bd0` and no other
wallet:

    setAgentURI(86957, "https://scvd.store/.well-known/agent-registration.json")

**The explorer has no edit flow.** This line used to say that was the
easiest path; it was checked on 2026-09-15 and it is not true.
`erc-8004.quicknode.com` is read-only for the owner — its only
Connect Wallet is for submitting feedback, and there is no Set-URI,
Manage or Configure control anywhere on the page.

The path that works is BaseScan, and two details decide whether it
works on the first try:

  - **Write as Proxy, not Write Contract.** The registry is an EIP-1967
    proxy (implementation `0x7274e874ca62410a93bd8bf61c69d8045e399c02`).
    The plain Write Contract tab lists the proxy shell's functions and
    `setAgentURI` is not among them — which reads as "the function is
    missing" and is not.
  - **Do not touch the `Scale` dropdown beside `agentId`.** It
    multiplies the field by a power of ten, for token amounts denominated
    in wei. An id is not an amount. One click on `x10⁶` makes the
    argument `86957000000`, and the call reverts
    `ERC721NonexistentToken` — the same error a wrong id gives, which
    reads as "the agent does not exist" and is not.

Connect the owner wallet at the top of that tab, press `Simulate`
first (it is free, and it is what catches a wrong connected account
before gas), then `Write`, with `86957` and the URL as the two
arguments.

same call re-points the URI any time.

## Verifying afterwards

Three checks, in the order that isolates a failure:

1. **Chain took it.** `tokenURI(86957)` returns the new URL. If it does
   not, the transaction did not land; nothing else is worth checking.
2. **The document is the one the chain names.** Fetch that exact URL and
   confirm `type` is
   `https://eips.ethereum.org/EIPS/eip-8004#registration-v1` and that
   `registrations[0]` reads `{agentId: 86957, agentRegistry:
   "eip155:8453:0x8004A169FB4a3325136EB29fA0ceB6D2e539a432"}`. This is
   the comparison every verifier makes; if it passes, the agent and the
   domain are bound in both directions.
3. **A reader agrees.** Refresh the explorer page. "Unconfigured" should
   become the store's name, description and services.

Steps 1 and 2 are the instruments and can be run by anyone. Step 3 is
an explorer's cache and may lag — per the verdict protocol in
AGENTS.md, a stale explorer page is testimony, not the record. If 1 and
2 pass and 3 still reads unconfigured after a cache cycle, that is a
finding about the explorer, and worth filing rather than re-sending the
transaction.

All three passed on 2026-09-15.

## Where the identity is published now

The registration file is what the CHAIN points at. It is not where a
reader who has never heard of agent 86957 would start, and for a day
it was the only surface naming the identity at all — findable only by
whoever already had the id. That is the same failure the trust
document was built for: facts published somewhere no checklist knew
to try.

`src/store/chain-identity.ts` fixes the direction of travel. Two
blocks, carried by the documents a diligence pass and an indexer
actually fetch — `/.well-known/trust.json`, `/.well-known/x402.json`,
and `/atlas.json` for the agent that has just arrived:

- **`chain_identity`** — the agent id, the CAIP registry string, the
  contract, and the `eth_call` payloads that read the agentURI and the
  owner straight off Base. No key, no account, no cooperation from us.
  Two third-party viewers are named beside them (the QuickNode
  ERC-8004 explorer and BaseScan), both opened and read from here on
  the confirmed date, each described by what it RENDERS rather than by
  any verdict it might imply.
- **`identity_surfaces`** — the same identity in every other
  vocabulary: did:web, the A2A card, the MCP server card, the OASF
  record, x402 discovery, the signing key, security.txt, owners.json,
  and the house ledger. Routing, not new claims. A test fetches every
  one and fails on anything that is not a live 200, because a dead
  link in the block that says who we are would be the strongest
  argument against the rest of it.

**No on-chain state is asserted in either block.** The agentURI is one
transaction from changing, so a cached sentence about what the
registry currently resolves to is a claim with a shelf life — exactly
what this store sells a desk for catching in other people's metadata.
The blocks publish the address, the id and the call; the chain answers
the rest, to whoever asks it.

**The explorers stay out of `EXTERNAL_RECORDS`.** That array promises
records that somebody INDEXED this store. A block explorer reading a
public contract is neither an index nor an endorsement, and folding
one in would be the store arguing with its own definitions — the same
reasoning that keeps `KEEPER_SOCIAL` out of it. A test asserts the
separation rather than trusting it to be remembered.

The identity is not a reputation, and the blocks say so in their own
`limit` field: an on-chain record proves an address registered this
agent and controls it. It proves nothing about the goods.
