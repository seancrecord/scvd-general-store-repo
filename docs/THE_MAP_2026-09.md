### Overlap that should remain explicit

- **Preflight → Once-Over → Refresh → Hosted Profile:** related endpoint evidence, different purchased work: a report, a new census row, or presentation for a term. The free passport and history remain free. The Once-Over now also reads other published surfaces, so “this exact free readout, signed” understates the paid scope (`src/services/surface-reads.ts`; roadmap S8).
- **Look ↔ Spot Check:** both use the recorded history; the look adds a live unpaid probe, the Spot Check preserves a signed historical copy. The look is not a free version of the whole paid catalogue.
- **Night Watch ↔ Conformance Watch:** both repeat structural probes for a bounded week; cadence, stored checks and drift views distinguish them. Neither purchases successful delivery. Opening Day bundles the Conformance Watch with Launch Check; it is not another battery.
- **Single attestation ↔ sheaf ↔ reconciliation ↔ Case File:** observation of settlement, volume packaging, ceiling comparison, then assembly. A sheaf cannot record a mandate. The Case File may lack the very delivery evidence a dispute turns on.
- **Conformance ↔ submitted-receipt verification ↔ by-id verification:** compact JWS from any issuer, submitted JSON in supported forms, and this store's own ids. The submitted-receipt checker already returns a **free signed verdict**. “Money always buys the signature” is therefore not a universal law of this catalogue.
- **Statement ↔ Operator's Statement:** same chain-reading job at different cadence; neither establishes that every incoming transfer was a sale. **Hello / fortune / blessing / lucky** overlap as client-test targets but remain different authored goods. Patronage certificate / standing pass overlap as support, with different duration and output.

## 3. THE FUNNEL, STATED AS A MECHANISM

### The shared paid spine

Arrival → a named free answer → an optional need for retained/extended work → `/menu/{item_id}` or `/menu.json` → `GET /api/buy/{item_id}` with the required inputs → published 402 accepts → caller chooses and signs → retry the same request with `PAYMENT-SIGNATURE` (the supported legacy header is also accepted), or the relevant `/mcp` `buy_*` cluster with `_meta['x402/payment']` → good/record/order → its returned report and verification URLs.

The source of required inputs is the generated contract, not this prose: `src/lib/bazaar-discovery.ts`, `src/lib/mcp-tools.ts`, `src/lib/shopping-fields.ts`, `src/routes/openapi.ts`. The caller should retain the returned URLs and exact signed bytes. Every menu item is routed through a shelf cluster and has `when`/verify fields; **0/32 menu items are structurally prose-only** by comparison of the menu ids with `ROUTES` and `SHELF_CLUSTERS`. Semantic relevance is a different test.

**Ordering law, precisely:** verified authorization and replay/idempotency checks run first; the handler does the fallible work; minting paths call `pending.settle()` at their last line before minting the signed purchase record. Non-minting paths settle after a successful handler response. This is “deliver first, settle after” as implemented, not a claim the certificate exists before settlement or that a later human report has already been written. Human-queue purchases create the order first; completion is polled free through `check_order`. Sources: HOUSE_RULES 9, `src/lib/payment-gate.ts`, `src/services/fulfillment.ts`, `src/lib/order-status.ts`; checks: `test/deliver-first.spec.ts`, `test/mcp-check-order.spec.ts`. The remaining mint/write boundary is explicitly acknowledged in the gate.

Refusal is a successful outcome when the evidence or the buyer's controls require it. A tier keeps its fraction and source rows; the store does not sort hosts by worth. Watches end; renewal needs another purchase. Neither client spend controls nor the free-only host surfaces are obstacles to bypass.
