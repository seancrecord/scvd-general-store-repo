# Assisted evidence workflow — October 1

The remaining harness integration is implemented as explicit `evidence_workflow: "sources-and-draft-v1"`. The prepared plan pins the verified npm x402-verify 1.11.0 runtime and its publication source commit. This is software validation and a frozen condition specification, **not a native qualification or buyer result**. No new buyer or recipient is launched by this record.

The condition is directed-only and requires package access plus the complete pinned runtime. Its source-selection prompt explains the existing offline `sources` command. Public index links stay unsigned; they neither select an original for the buyer nor prove absence. Online capability qualification must actually exercise the installed helper on synthetic data; retained output is independently reproduced in full.

Offline recipient qualification now exercises the saved-draft flow on a newly generated synthetic signed original in addition to its existing local cryptography task. It uses the same offline adapter and budgets. Generic cryptography success without the draft check remains incomplete. Supplied synthetic files are qualification machinery, not additional buyer evidence.

For a new recipient, the model chooses an inventory original and public verification key, saves its exact proposed final as `evidence/recipient-draft.md`, and records the selection in `evidence/recipient-check-request.json`. The supplied standalone Node command runs the pinned CLI's `--check-identifiers`, saving full JSON output and stderr. It grants no network or installation permission. The model may revise and recheck within the existing budget, then returns the saved text byte for byte.

The controller uses the existing bounded evidence collector, preserving draft, request and output outside the model workspace. It independently replays verification against the original immutable handoff inputs, checks visible execution of the supplied command and compares final text against the draft. Both draft and final hashes are recorded. Missing, tampered, unbound, unrecognized or different results leave completion incomplete. A stopped attempt retains `last-message-verbatim.md`, never a falsely labelled completed final. Completed final text is retained separately as `final-verbatim.md`; the raw trace remains canonical.

This guard does not verify prose, labels, attribution, dates, issuer identity or freshness. The underlying identifier check covers whole ASCII hexadecimal tokens of at least 48 digits; it excludes short, split and non-hex identifiers. Legitimate identifiers outside the selected original/key reference set need review. Existing semantic review and acceptance requirements remain mandatory. A tool-level pass is not a buyer pass.

## Compatibility and validation

Absent the condition flag, earlier prompt text and behavior remain unchanged. Before/after rendering of seven closed 1.9.0 plans using their hash-pinned retained runtime reproduces identical buyer, online capability and recipient prompts and recipient adapter arguments; see `prompt-compatibility.json`. Existing plan/protocol/instrument hashes prevent old qualification from authorizing this changed condition. The new module is included in the frozen instrument. Native budgets remain four minutes/20 calls for buyers and three minutes/12 calls for recipients; models, zero spend and the fourteen-day policy are unchanged.

Regression controls cover missing/old runtime, unknown conditions, draft retention, exact final comparison, missing checks, changed reports/requests/originals, absent command execution, symlinks, missing or changed plans, interrupted runs and both positive/negative offline qualification. Initial prompt/validation tests failed before implementation; reverting the runner changes and removing source-output replay each reproduced failures. Stopped and missing-terminal message controls were also witnessed red before their fixes. All 322 buyer tests, typecheck and both Worker dry-run bundles pass. The first sandboxed full buyer run could not bind an existing loopback HTTP fixture; the complete suite passed with that fixture permission. Hosted four-shard CI and aggregate check remain required before merge.
